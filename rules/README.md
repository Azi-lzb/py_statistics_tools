# 开发维护规则入口

## 必须查阅

本目录规则适用于本项目的新增功能、缺陷修复、维护、重构、依赖升级和打包调整。编码前必须阅读 [表格文件读写与修改技术选型规范](表格文件读写与修改技术选型规范.md)，并按其操作编号确定本次涉及阶段；只修改文档时核对规则和链接，不要求运行业务性能测试。

## 开发维护时主动检查效率

1. 先按规范第 1 节确认母子项目策略，再从第 8 节定位本次菜单、代码入口和测试；检查直接调用链，填写第 2 节契约及 write_pattern/data_owner，按 W01 条件分支和 Python/Rust 数据边界选型。已有需求和配置能够确定的信息直接使用；测试代码存在不等于已有真实验收报告。
2. 检查是否重复打开/保存同一工作簿、逐单元格跨进程调用、无必要地创建 DataFrame、为只读值启动 Office/先转格式、缓存失效、宽泛异常回退，以及现有后端缺少的保真能力。检查范围以本次功能和直接调用链为限。
3. 发现耗时热点、未满足的资源预算或具体能力缺口时，必须在本次方案中主动给出技术调整建议。说明受影响功能/阶段、当前技术、候选技术、支持的格式/系统、保留项、实施范围和验收方法。引用实际代码或计时证据；未测量时明确写“尚未测量”，先给出分阶段测量方案，禁止虚构提速倍数。
4. 没有技术调整依据时，说明“本次涉及流程未发现有证据支持的后端迁移”，并继续完成当前任务；不为了产生建议而更换库或扩展任务范围。
5. 已获用户授权的优化或必要修复，应完成实现、对应功能回归和保留项对拍。跨功能迁移、输出语义变化、新增外部应用依赖超出当前授权时，先完成可审阅的方案并说明影响，再由用户决定范围；既有授权不得重复请求。
6. 同一输入输出契约已有多个适配验收通过的后端时，方案必须说明默认后端和用户备选，按规范第 6 节提供按阶段选择、设置持久化与失败处理；不在每次启动重复询问，不暴露未验收后端。
7. 实际实施技术迁移时记录读取/计算/写入和端到端耗时、内存、环境与输出差分，按规范第 9 节判断是否切换默认。保留已验证的 Calamine/Direct OOXML 路径，不以“改成 Rust/openpyxl”本身当成效率成果。
8. 交付说明列出实现与建议分别覆盖的功能、实际验证结果和未执行的平台；将母项目及子项目对外功能变化记入母项目现有版本日志。仅开发规则变化写规则/规范修订记录，不升级产品版本。

## 技术方案最小内容

- 输入输出、保留项、操作编号与平台。
- 当前调用位置、耗时证据或待测阶段。
- 默认方案、同契约用户备选和选择理由。
- 适配工作、兼容性缺项、验收与性能指标。
- 已授权实施范围；超出范围的工作单独列为后续建议。
